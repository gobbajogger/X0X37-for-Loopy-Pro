## Exact storage reduction, not quality reduction

The two Chicago A/E arrays have 32,770 binary32 coefficients: 131,080 raw bytes. A private generator pins the original derived-table manifest and hashes, then encodes independent 32-entry blocks using first-value bits plus bit-packed zigzag modulo32 deltas. No sample, coefficient, interpolation or precision is discarded.

Measured payload plus block directories: **59,186 bytes**, saving **71,894 bytes** of data. The pi32v2 provider object adds 40 bytes of readonly descriptors and 90 bytes of code; decoder code is 280 bytes. The MP4 reader dispatch increases its text by 90 bytes relative to the accepted raw-table component. Net measured section difference is **71,394 bytes saved**, before final link/alignment. This is not a final application fit claim.

The alternate MP4 table reader uses exactly the same cutoff index, preparation arithmetic and state update as the existing array reader. All 16,385 indices and subsequent filter sample states match bit-for-bit. Existing raw-array callers remain supported. A future qualified target integration must select only the packed provider, omit unused raw A/E symbols, and verify the actual final map and reserves; merely adding compressed data alongside raw arrays would save nothing.

Lookup needs no table-sized RAM buffer and decodes at most 31 deltas per queried coefficient. This is control-preparation work, not per-audio-sample decoding. Host cost is recorded separately from target section measurements; no device CPU improvement is inferred.
