## Five USER-TASK friction findings (each is a review hypothesis grounded in observed live source, not an unperformed usability test)

### UT-01 — Choose exactly the right physical instrument and meaningful firmware version (P1)

**Observed:** Main installer blob `fe3350b2`, lines 472–485: “Choose the right firmware,” physical-model radio group, “Choose the name printed on your keyboard,” package-version dropdown; nightly blob `265bad08`, lines 491–504 similar with a connection-identity check disclosure. Main catalog blob `fadfe387` uses a SHA-tagged `nightly-79280e76-dev` entry with user-facing 0.0.25.1; nightly `24a8b208` uses `nightly-94197fc8-dev` / 0.0.26 with unverified hardware boot. Live templates also expose build/test metadata behind package detail; inspect presentation hierarchy on an actual browser before claiming visible clutter.
**Friction:** New owners cannot infer what a SHA-tagged developer build means, which update is safe, or why a connected Pro-reported identity may not prove a physical Elite. Mistakenly treating an unverified candidate as a normal update is high-consequence. This is not license for auto-guessing physical model.
**Baud Girl mechanism and tradeoff:** Test connection before version selection; offer only device-specific built versions (manual §13.1). This reduces mismatch choice, but DnBOX must retain physical-label confirmation where USB aliases can misidentify Elite as Pro. No automatic override.
**Smallest remedy:** One primary DnBOX versioned download/install choice with actual software version, supported physical model and honest availability; keep dev/hardware-untested candidates explicitly marked on NIGHTLY, not equated with a stable release. Put commit, digests and QA receipts in details, not the main hero. Explain the physical label check exactly once before write. Distinguish downloadable package from installed success.
**Acceptance:** Main and nightly each select Elite and Pro, with a wrong-model negative check, physical-label discrepancy check, missing-model version check, and no path that silently treats 0.0.26 boot-unverified as validated. Download names and information identify **DnBOX version and exact model**; matched file bytes/approval recorded in details. Evidence: screenshots and DOM assertions on exact Pages blob revisions, not hardware proof.

### UT-02 — Explain browser permission and test the connection *before* committing (P1/P2)

**Observed:** Both live Pages templates show “Step 01 / Connection” and a Connect button (main lines 459–469; nightly lines 478–489), followed by firmware and install steps. Source contains actionable `open`, `notfound`, `ambiguous`, `lost` and `model` cases (main ~980–1116; nightly ~1010–1138). Earlier source 94197fc8 has separate “browser cannot do it,” SysEx denial, cable and competing MIDI-app messages; this is historical, **not** proof those exact strings appear on live Pages. No live permission prompt was triggered in this review.
**Friction:** Chrome/Edge permission prompts, SysEx approval, a charge-only cable or a DAW holding the MIDI port can feel like firmware failure. Permission denied must not be conflated with unsupported browser or lost USB.
**Baud Girl mechanism and tradeoff:** Browser compatibility matrix and explicit third-stage Test connection before version choice; users know whether the tool can operate before deciding to install. Extra step costs a click but avoids a costly failed write attempt.
**Smallest remedy:** Dark, prominent browser support/preflight → Connect → explicit read-only identity/test result. On denial, explain how to retry permissions; for unsupported browsers, link a compatible browser workflow. No permission demand on initial landing.
**Acceptance:** On exact main/nightly revision, exercise browser unsupported, SysEx denied, canceled picker, charge-only cable/no port, competing MIDI app and two possible devices with mocks/read-only observation. Each outcome must say what failed, what was not written, and a specific next action. Never call failure “install started” when no write occurred.

### UT-03 — Backup and restore should be a user-visible contract, not hidden optimism (P1)

**Observed:** Main `fe3350b2` lines 505–507 warns first installs may replace prior working data and links “Back up important samples”; sample and project workspaces are separate (lines 454–455). Nightly `265bad08` lines 524–532 likewise warns and has `backup-warning` alert. Live source includes `backupSlots`, `restoreMapped`, readback mismatch and sample-snapshot authorization (main ~1979–2069; nightly ~2081–2150). A browser source path proving backup operations exists; no live sample extraction/restore was run. Separate project export and sample-slot preservation have different scopes.
**Friction:** “Backed up automatically” can be heard as “my entire song is safe.” User may not understand what files to keep, whether a restore succeeded, or how recovery-mode limitations differ from an ordinary reinstall.
**Baud Girl mechanism and tradeoff:** Explicitly promises stock presets/patterns save-and-restore where supported and instructs users to save current unsaved work (manual §13). This is strong expectation management, but DnBOX projects, sample slots and flash partitions differ; do not copy the guarantee.
**Smallest remedy:** Just before install show a concise per-data-type statement: samples, projects/song arrangements, settings, and unsaved edits, each with actual preserve/backup/manual-export/unknown status. Require an independently verified backup for at-risk readable occupied slots; provide a clear filename and restore path. Keep exact snapshot and CRC/digest proof in collapsible details.
**Acceptance:** first install with occupied slots, empty slots, blocked/failed backup, partial restore, no-space restore, reboot recovery and separate project export. Never show full success if any required restoration fails. Validated archive reopening remains mandatory where specified. No claim that all project bytes are preserved unless demonstrated.

### UT-04 — Restart wait and recovery mode need a state-specific explanation (P1)

**Observed:** Live Pages main `fe3350b2` lines ~1222–1251 distinguishes initial transfer, OTA-loader appearance, second-stage transfers, and app return; same in nightly `265bad08` ~1243–1272. Main throws `noloader` (“replug ... stays in update mode”), `noreturn` (power-cycle), `stopped`, `lost`, and `mismatch`. Both have read-only device binding across re-enumeration. These are source-level state distinctions, not measured timeout adequacy.
**Friction:** Normal USB disconnection/re-enumeration during firmware flashing looks exactly like a broken device. A generic “replug and retry” can invite unsafe repeated writes when stage is unknown.
**Baud Girl mechanism and tradeoff:** Explicit six-step installation and manual explanation that Firefox loses the FM-1/SMK-37 across restart; browser selection avoids a predictable reconnect failure. A fixed one-minute estimate from Baud Girl is NOT evidence of DnBOX's timing.
**Smallest remedy:** State-aware progress: “switching to updater,” “writing,” “waiting for keyboard to restart,” “verifying it returned,” and distinct recovery instructions for app, loader and absent device. On timeout, describe *observed* stage and recommend safe checks without claiming a brick. Never automatically repeat uncertain authorization.
**Acceptance:** Mock stalled loader, delayed re-enumeration, device loss pre-write/during-write/post-write, unexpected second keyboard and loader-only recovery. Timeout labels and next action must reflect the state and never imply verified failure/success without readback.

### UT-05 — “Done” is only done after **boot identity and data state** are verified (P1)

**Observed:** Live main `fe3350b2` ~1244–1251 and nightly `265bad08` ~1265–1272 already check the returned product after reboot, distinguish still-in-loader from app mode and throw `mismatch` for the wrong returned product. Main/nightly catalogs explicitly mark available test candidates `hardware_tested=false`. Source checks cannot establish that the screen fully booted or sound/music works.
**Friction:** USB transfer completion, returned MIDI identity, booted running instrument and restored musical state are **four different levels of assurance**. Users can mistake a downloaded package or transfer completion for playable DnBOX.
**Baud Girl mechanism and tradeoff:** Sixth Done stage, with prior explicit browser/connection/installation stages. DnBOX should preserve this clarity but show honesty where end-to-end device boot proof is unavailable; cannot use a friendly checkmark to invent hardware verification.
**Smallest remedy:** Report “firmware transferred,” “device reconnected and identity checked,” “samples restored/verified” separately. Only fully verified conditions earn complete success; where actual screen/audio boot is not instrumented, request a simple user visual confirmation, labeled as such, and route failures to specific recovery. No raw hardware evidence hashes in the main landing.
**Acceptance:** Prewrite cancel, verified transfer but no app return, wrong returned identity, returned correct identity but restore failure, and successful readback+restore each display distinct outcomes and steps; full success NEVER follows transfer-only evidence. Human visual boot confirmation must not masquerade as automated proof.
