## Confirmed new keyboard defect and narrow repair

`main_fm1.c` starts TIMER5, waits30ms, optionally runs setup, waits300ms, initializes UI, then first calls `smk_frame`/`smk_faders`. Input frames advance once each16 timer ticks at10kHz. Normal first application scan is therefore already at least206 input frames. The `<200` settling branch cannot guarantee initialization of static fader history.

Installed first scan: saved909 level64, parked decoded fader100, frames206, no preceding gesture. `last[0]` initially encodes pending plus synthetic previous0. The crossing check invents0→100 crossing64 and issues one real engine write; saved/display level becomes100 and actual mixer gain changes0.4096→1.0. This is an independently reproduced sound-parameter change, not a UI-only assertion. It explains a reachable startup failure; it does not establish the cause of every later intermittent report.

Repair: reuse bit1 of the existing `held` byte as a one-time unknown-history marker. First application call takes the existing project-busy sample-seeding path, records all physical positions as pending, consumes the bank button, and returns without writes. Subsequent `held` values are Boolean0/1. Existing target selection, pickup tolerance, crossing, live writes, motion hold and mappings stay intact. No additional static variable, smoothing, protocol or project-format change. `smc_mixer.c` is byte-identical to installed; PR196 is neither duplicated nor edited.

Missed conversions retain previous raw/filter/decoded state until fresh samples arrive. A long gap can hold a stale position and then catch up. Two consecutive bad samples can pass the median. Neither phenomenon was observed on hardware here; the host model cannot certify electrical settling, SPI completion, interrupt latency, actual ADC freshness or all possible streams. No blanket filtering change is justified.

## Muting: additional confirmed mismatches and proposed separate scope

Part/drum mute is separate `seq.mute`/`seq.vmute`, not a cached level restore. Already-acquired fader64→mute→80→unmute retains80 correctly. Untouched parked100 with saved64 resumes64 correctly. Pending fader100→mute→110 without crossing64 is rejected and resumes64; this conflicts with the owner's requested moved-while-muted behavior, but is normal existing soft takeover rather than lost accepted writes.

FX reverb/delay mute instead writes the parameter to0 and remembers `fx_restore`. Even a previously acquired64→mute→80 cannot acquire target0, and unmute restores64. This is a distinct cached-level/target aliasing problem and persists with PR196. M8 controls `FX_VOLUME`, while physical fader8 controls the master FILTER; those must not be conflated.

Proposed separate repair: keep the intended level authoritative and represent mute independently. Accepted edits, including while muted, update that intended value while output remains muted; unmute applies it without restoring an older cache. For a previously pending SMC control, grant takeover only on a genuinely changed sample for the same muted destination during an unchanged mute epoch. First/duplicate parked packets must not claim it. A real external value/target change or navigation to another destination ends that exception and retains normal soft takeover. Lock follows the captured destination; repeated toggles must be idempotent with no level writes from untouched faders. FX output gating must cover keyboard edits and motion too, not only SMC packets; zero alone cannot identify an explicit mute.

This mute design is **proposed, not implemented or qualified by the startup fix**. It is deliberately not silently folded into the small reviewed startup change: it adds shared FX output ownership and a muted-gesture policy beyond the existing cache. Parent owns the next bounded implementation/integration assignment. The replayable `SMK_FADER_MUTE_AUDIT=1 sh tests/host/smk_fader_state_test.sh` probe reports actual behavior and desired mismatches; it is not a passing desired-behavior regression. Exact PR196 replay covers182 observations with75 desired mismatches and intentionally exits1. It includes both drum kits, reverb/delay, acquired/pending, moved/untouched, locked page navigation, external target edit followed by noncrossing movement, repeated mute pairs and volume/filter separation. In particular, an FX external edit to90 while muted makes the current next button press set0 rather than unmute: zero is currently both value and mute identity. Counts enumerate a bounded policy matrix, not independent hardware faults.
