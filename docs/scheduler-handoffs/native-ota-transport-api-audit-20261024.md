# Production OTA transport API audit — 2026-10-24

Status: read-only independent source/API review. No device, flashing, native USB transfer, firmware build, backend enablement, or complete-root QA is asserted here. Reviewed repository base: PR121 `2e8c2795ffab81d663890e2ed3b88f470da924de`, incorporating PR114 R9. This audit does not replace Data Safety, sole Independent QA, or Safe Merge acceptance.

## API conclusions

1. **Mido 1.3.3 names do not bind a native endpoint atomically.** `_open_port` resolves a display name with `port_names.index(name)` then invokes `rt.open_port(port_id)`. ALSA also expands abbreviated names. Native enumeration can change between these operations. An exact display-name check before opening does not remove this index race. [Source lines 78–110](https://github.com/mido/mido/blob/1.3.3/mido/backends/rtmidi.py#L78).
2. **python-rtmidi 1.5.8 exposes port indices, not an authenticated input/output unit pair.** `open_port` forwards the integer to C++ `openPort`; `is_port_open()` checks wrapper `_port` state. These operations supply no cross-reboot identity. [Source lines 530–582](https://github.com/SpotlightKid/python-rtmidi/blob/1.5.8/src/_rtmidi.pyx#L530).
3. **RtMidi 6.0.0 ALSA output is a subscriber broadcast.** `MidiOutAlsa::openPort` creates a local port with READ|SUBS_READ and subscribes the chosen receiver; `sendMessage` uses `snd_seq_ev_set_subs`, so additional subscribers can receive the message. Therefore an opened RtMidi output does not prove an exclusive physical destination. This is a source/API property, not an executed hardware reproduction. [Open source lines 2458–2534](https://github.com/thestk/rtmidi/blob/6.0.0/RtMidi.cpp#L2458), [send source lines 2580–2643](https://github.com/thestk/rtmidi/blob/6.0.0/RtMidi.cpp#L2580). ALSA explicitly permits dynamic routing and third-client subscription changes; `snd_seq_ev_set_subs` broadcasts to subscribers. [Official sequencer contract](https://www.alsa-project.org/alsa-doc/alsa-lib/seq.html), [middle-level API](https://www.alsa-project.org/alsa-doc/alsa-lib/group___seq_middle.html).
4. **CoreMIDI is more directly endpoint-bound after opening, but current wrapping is insufficient.** RtMidi saves a `MIDIEndpointRef` destination and later calls `MIDISend` with it. It still chooses that reference by a mutable index during opening. Client creation uses NULL notification callbacks; input connection source-ref is NULL, and callback discards source-ref context. No source conclusion here establishes that a persistent CoreMIDI object identifies the same physical keyboard after USB replacement. [Core open lines 1554–1601](https://github.com/thestk/rtmidi/blob/6.0.0/RtMidi.cpp#L1554), [send lines 1680–1725](https://github.com/thestk/rtmidi/blob/6.0.0/RtMidi.cpp#L1680), [input lines 1190–1255](https://github.com/thestk/rtmidi/blob/6.0.0/RtMidi.cpp#L1190). Apple's [UniqueID documentation](https://developer.apple.com/documentation/coremidi/kmidipropertyuniqueid) describes system-assigned MIDI-object identifiers, not a manufacturer-authenticated serial or same-unit reboot attestation.
5. **libusb is a credible candidate for the separate same-open-handle problem.** Its operations use a device handle, and transfer APIs return NO_DEVICE after disconnect. Linux implementation retains one usbfs fd and handles POLLERR through `usbi_handle_disconnect`; it does not reopen a name for every send. This does not prove safe enumeration→open association under every OS race, and does not bind a newly enumerated loader. [Official handles contract](https://libusb.sourceforge.io/api-1.0/group__libusb__dev.html), [transfer errors and partial transfers](https://libusb.sourceforge.io/api-1.0/group__libusb__syncio.html), [pinned core.c lines 1389–1435](https://github.com/libusb/libusb/blob/v1.0.29/libusb/core.c#L1389), [Linux opening lines 1410–1434](https://github.com/libusb/libusb/blob/v1.0.29/libusb/os/linux_usbfs.c#L1410), [disconnect lines 2725–2764](https://github.com/libusb/libusb/blob/v1.0.29/libusb/os/linux_usbfs.c#L2725). Port topology is explicitly a physical socket property; different devices can share the same returned path after replacement. Never use it as unit identity.

## Existing firmware inputs and legacy bootstrap

At the reviewed repository base, `firmware/src/usb.c` lines 240–252 set USB descriptor index 16 (`iSerialNumber`) to zero in CDC and non-CDC variants. Loader includes this same source. `firmware/src/ota.c` answers handshake with `FELUCCA_ID`; no unit/session proof is returned. `firmware/hal/fm1_flash.h:130` reads JEDEC manufacturer/type/capacity via 0x9F, not a chip UID. `firmware/src/ble.c:232` hashes the protected USRTRIM calibration record through `ble_addr_of` (`firmware/src/ble/ble_glue.h:96`). Two CRC32 seeds generate a static BLE address; comments claiming different records between units are not a manufacturing uniqueness guarantee or authentication. The failed-flash fallback hashes an identical one-byte record. Do not publish raw trim/key_mac data or promote those hashes to trusted identity.

A potentially useful **design investigation**, not an implemented/qualified flow, is a session-personalized loader. Existing X0X `ota_stage()` accepts its marked loader, validates its bounds/CRCs, stages and verifies it, then commits after host confirmation. A newly designed loader could carry a fresh host nonce in its package and require it on every destructive request; the host would accept only that nonce at the new loader endpoint. This could support a legacy X0X bootstrap only if the initial package and UPGRADE are first guaranteed to travel solely to a verified, already-open A handle. New firmware cannot retroactively authenticate an old-firmware endpoint selected by name/index. The current source gives no proof for arbitrary stock/legacy versions' acceptance of a personalized loader, and no such compatibility should be asserted.

Personalization requires a specified bounded loader data slot, checksum/package updates, actual pinned Elite/Pro target builds and budgets, nonce entropy/length and replay policy, mandatory protocol gating (no legacy destructive fallback), interruption/recovery design, and binding through final application/sample restore too. An echoed nonce is session continuity under the accidental-misrouting threat model, not cryptographic unit authenticity against malicious firmware. New protocol guards alone do not prevent B receiving a destructive legacy UPGRADE before session negotiation.

## Required observations before enablement

- Verify real platform/driver/version and the exact opened device object; bind both USB-MIDI directions from that one handle. Do not rediscover or automatically reopen after disconnect.
- Demonstrate harmless traffic with A/B same-name units: replacement before/during open, disconnect while sending, old handle after B replacement, and queued B→A callback. Observe B receives zero destructive frames; use a simulator/read-only captures before any separately authorized real flash.
- Separately demonstrate cross-reboot continuity using a specified supported mechanism. Correct app→loader rename, foreign identical loader, stale loader, wrong/replayed session, Elite/Pro destination model and supported migration all require tests.
- Prove interrupted backup/write/restore preserves the archive and never restores slots onto B. Final application identity requires the same continuity chain; a matching package string is insufficient.
- Record legacy installed version and its actual bootstrap behavior, without treating a newly built app's future capability as proof about the old version.

No `/dev/snd` or `/dev/bus/usb` was present in this audit environment. Native ALSA extra-subscriber and USB unplug/replacement observations were NOT RUN. A Linux kernel-source fetch returned HTTP 429; no kernel guarantee is claimed from that absent source.
