# Two-peer HCI transport prototype

Base: `272b80fbc38ac8be7e6adac96fe990394c1934f8`. This is source and host-test work; no device was scanned, paired, flashed or tested.

`blec_bus_t` owns two independent central records and one HCI command arbiter. Only peer 0 bootstraps controller setup and Reset. A later link joins at the existing scan stage. Scan/initiation ownership lasts through the connection outcome; identical command opcodes are routed to the owner of the sole accepted command. Command Complete/Status credit gates submission. Mailbox rejection leaves state retryable. Fair alternating polls preserve ACL progress while another link scans or fails. A missing command completion sets `command_fault` after 3 seconds, retains its owner, and permits existing ACL traffic. Only a matching completion reconciles that slot; an unreconciled fault requires controller/radio recovery, rather than guessing a delayed identical opcode's owner or resetting a surviving link.

The shared ACL pool subtracts only accepted mailbox sends. Per-handle outstanding counts bound completed-packet refunds; disconnect refunds only its own outstanding debt. Invalid/truncated frames and unrelated handles do not refund credits; excess completion counts are clamped to tracked outstanding. An in-range duplicate completion is indistinguishable from a real completion, so ordered, nonduplicating HCI is required. Handle zero has a separate validity flag. Connection Complete and Enhanced Connection Complete have exact size checks. Generation counters describe observed link admissions, not extra identifiers on the HCI wire. The controller and mailbox must supply the ordered HCI stream: Disconnection Complete retires that connection and its outstanding buffers; an old-session completion after the same numeric handle is reused is not distinguishable from a fresh completion on the wire. This is a protocol precondition, not claimed protection against an arbitrarily reordered or corrupt controller stream.

Peer 1 is denied by default. `blec_bus_allow_peer` admits an exact address and type only before bus start. Firmware's additive `plat_ble_smc_peer_target` accepts only peer 1 and only in boot/configuration context before `ble_start`; no old device identity is persisted or inferred. There is no new UI or automatic second-device name discovery. The owner must identify and approve the actual devices before a test harness supplies the target. Peer 0 retains existing single-SMC name discovery, with duplicate live addresses excluded. Link edges publish after every received frame, and a MIDI callback publishes a new up edge before the first new-session ingress.

The real JieLi SDK pin `d179b4484759423312073f5fbb232501aa491047`, `apps/common/config/log_config/lib_btctrler_config.c` lines109-128, enables master multilink and sets total hardware links plus five RX and ACL buffers per link. The candidate follows that source with `hw_nums=2`, `master_multilink=1`, `rx_nums=10`, `acl_total_nums=10`, preserving the existing LE roles and feature policy. These settings alone do not prove controller capability.

An actual offline pi32v2 controller link with the unchanged 64KiB flash and RAM/heap/stack limits FAILED: no undefined symbols, CFLASH overflow1144 bytes. Failed map sections: text54912, rodata6360, ramtext3512, data1816, bss6284 bytes. Image end `0x02097478` gives66680 bytes. RAM end `0x01c07ce0` leaves544 bytes to `0x01c07f00`; heap10112, run stack2048 and ISR stack2048 remain reserved. Dynamic heap demand and target timing were not measured. No successful controller image exists from this configuration.

The same pi32v2 compiler measured `sizeof(blec_t)=348`, `sizeof(blec_bus_t)=776`, `sizeof(bleh_t)=792`; the bus fits the existing peripheral-host union with16 bytes spare. This is structure evidence, not a complete application budget.

Native production-source test: `cc -std=c99 -O1 -g -Wall -Wextra -Werror tests/host/ble_multi_peer_test.c -o /tmp/ble-multi && /tmp/ble-multi`:79 checks, zero failures. Repeating with `-fsanitize=address,undefined` also passed. Production state-reporter extraction also passed six scenarios, including a live second peer while the first is starting or failed. The traces distinguish bootstrap-only Reset, command owner/backpressure, two live senders, bounded completion credit, rejection, disconnect/refund, handle reuse in ordered HCI, handle zero, malformed enhanced completion, first-link survival, exact target admission, notification routing and timeout-degraded ACL progress. `python3 tools/check_locked_settings.py` passed20 settings. These tests do not qualify current-control integration, audio timing, full Elite/Pro budgets or hardware capability. Independent QA and a fitting matching controller remain required.

Command credit-only opcode0 events follow [Bluetooth Core HCI command flow control](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/host-controller-interface/host-controller-interface-functional-specification.html): renewed command allowance does not complete or transfer an outstanding command. The production test covers allowance restored from zero and an announcement while another command remains owned.


## Accepted asynchronous Create recovery

A local Create timeout or failed Cancel submission is not a controller outcome. The bus now records accepted Create separately from the HCI command slot and retains its scan/init owner through terminal LE Connection Complete. A successful Cancel Complete still waits for that terminal event. Scan parameters, scan enable and another Create remain blocked during that wait, including attempts by the same owner. Successful scan-enable completions also record whether the global scanner is active; FAILED alone cannot transfer an active scanner.

A terminal success after local failure/cancellation is routed to the original target owner and enters bounded Disconnect cleanup, rather than silently losing the controller handle. Terminal failure retires the pending procedure and permits a later fresh scan. A missing terminal outcome remains explicitly quarantined; existing peer ACL traffic continues and no Reset is sent.

`ble_async_create_test.c` submits the real Create, receives successful Command Status, then rejects every Cancel mailbox submission through both local deadlines. Against exact previous transport `545164bb22afdcbe69e3b622c65378b36a5bedf5`, it exits1 with owner255 (lost). Against repaired source it exits0 retaining owner1. The expanded79-check production trace covers late successful connection cleanup, Cancel Complete before terminal failure (no intervening scan), active-scanner quarantine and surviving first-peer traffic. Native and ASan/UBSan runs pass; the six production state scenarios still pass. Independent QA and current combined native builds must consume this new source before acceptance.
