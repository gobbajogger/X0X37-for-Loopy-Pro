# Optimization Watch: BREAK-slice Note Off ignores current MIDI-source ownership

**Date:** 2026-10-23 · **Scope:** documentation-only independent regression research · **Production base:** [`main@c9718ae833eb64a5191c350922593df8a36017c9`](https://github.com/gobbajogger/X0X37-for-Loopy-Pro/commit/c9718ae833eb64a5191c350922593df8a36017c9). **Status:** source-confirmed and native-host reproduced; physical incidence **NOT MEASURED**. No firmware, installer, Pages, controller, samples or project state changed.

## Executive summary and priority

**P2 — cross-input BREAK slice ownership, for the SMC/MIDI transport specialist and Independent QA.** A BREAK slice's most recent Note On can belong to Bluetooth, yet an older or unrelated USB Note Off for the *same slice* still clears the live held-key state. The opposite USB/Bluetooth order fails too. This is a distinct BREAK-slice manifestation of the source-ownership problem previously reported for the two 303 parts; it is **not** another queue-saturation or BLE packet-loss measurement. If both inputs route the BREAK channel during an X0X performance, the wrong port can potentially interrupt a keyed slice.

The project explicitly tracks `src_held[0]` (USB) and `src_held[1]` (Bluetooth) in [`engine.c`](https://github.com/gobbajogger/X0X37-for-Loopy-Pro/blob/c9718ae833eb64a5191c350922593df8a36017c9/firmware/src/app/engine.c#L490-L493). A BREAK Note On assigns the active slice to its most recent source, but [`midi_in()` BREAK Note Off](https://github.com/gobbajogger/X0X37-for-Loopy-Pro/blob/c9718ae833eb64a5191c350922593df8a36017c9/firmware/src/app/engine.c#L623-L631) unconditionally invokes `breaks_live(..., down=0)`, clearing the bit in [`breaks.c`](https://github.com/gobbajogger/X0X37-for-Loopy-Pro/blob/c9718ae833eb64a5191c350922593df8a36017c9/firmware/src/dsp/breaks.c#L456-L464), then clears that ownership bit for *both* inputs. There is no source-owner guard on ordinary Note Off. Conversely, the existing link-end path releases only the notes whose owner matches the disconnected input. This discrepancy is testable without BLE starvation.

## Safe proposed fix and remaining risks

A separately owned SMC/MIDI implementation should apply the same source-owner guard to BREAK-slice ordinary Note Off that source-specific disconnect already uses: a release from the nonowner must not turn off a key still held by another input. Define behavior for simultaneous same-slice presses, repeated Note On, per-source disconnect and a single-input genuine release. Add a negative regression for each direction, unowned Off, unrelated slices, clip mode off/on routing, and both existing `usbnotes`/`blenotes` scenarios. A distinct implementation-owner patch must be independently reviewed against any recent SMC/clock branches and tested on an exact integrated source tree before native Elite/Pro build/model/controller/RAM/pool/flash and distribution/backup/restore checks are meaningful.

**Unresolved physical-only questions:** whether user performance routes both transports to BREAK on the same MIDI channel, actual voice/audio change after an incorrect release, BLE/USB scheduling and latency, audio XRUNs, hardware clip/pad LED effects, and true sample/slot preservation. The two-transport host simulation does **not** establish frequency in normal performances. Production firmware distribution remains separately restricted to attributable model-matched owner hardware PASS and approval. No firmware fix, target build, hardware flash, Pages publication, data migration or sample modification is claimed.
