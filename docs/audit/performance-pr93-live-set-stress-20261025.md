# Performance Engineering R15: BREAK live-set stress (producer evidence)

**User-visible goal.** A musician must be able to reverse a BREAK loop, change pitch and tempo, press and release live slice keys, retrigger, replace a sample bank and stop playback without hearing newly introduced glitches after the R13 reverse fast-advance optimization.

**Current affected source.** This test is pinned to PR #93's R14 parent `61740dbbc666396fbbe41df66effcf758c2ae45a`, Git ROOT `b42b6f6cd94fb1c642c334abdcfa3b95053dccdb`, compiled `firmware/` subtree `ee863f9cba6cbfb4e471d199ae408c7694acbac5`. Both optimized and legacy builds compile the *same* production `breaks.c` blob `9e1e607e2ddc3028383bfb6ebc85fbc7ac6864c5` with `BRK_FAST_REV_SKIP=1|0`, respectively. The runner rejects changes to six source/dependency Git blobs. No implementation or compiled firmware input was modified in this stage.

**New stimulus.** Four loop lengths (65, 4097, 176400 and 2116800 samples) × four fractional-rate profiles (31.875, 32.125, 64.875 and 257.125) × 320 callbacks of 64 frames = **16 scenarios and 5120 callbacks per executable**. Events include reverse on/off around two-ms fades, live slice NoteOff, half-speed, pitch from -12 through +12, tempo alternation 0.875×/1.125×, pinned slices, same-bank generation replacement, transport stop, quiet and zero-valued STOP output. ADPCM input is seeded synthetic bytes only; no actual user samples are included.

**Actual normal native outcome, Linux host.** GCC and Clang `-O2 -ffp-contract=off -Wall -Wextra -Werror -pedantic` each compiled and executed both paths with exit **0** (four compile and four run exits). All four raw synthetic PCM traces have the identical SHA-256 `53132ce8dd317793f74ed4eaf86a60b51574b4c538e4afd6205f4415a40cc516` (1,310,720 bytes each). Every scenario was audible before STOP, all STOP checks were silent, and all four missing-command negatives exited **2**. Original / optimized differ in decoder workload but no PCM output was changed by the fast path in these tested cases.

**Inherited sanitizer issue: already owned, not a new patch.** The unmodified public PR93 `fastmath.h` (`7d2e41bf70590bafa8af0a7376bb912bf763b098`) raises UBSan `left shift of negative value -1` in `fm_exp2_nf`, line 57, on both GCC and Clang in both paths; original sanitizer executables were **FAIL**, not PASS. This is already independently reproduced and owned by existing draft **PR #28**, not copied to the PR93 firmware inputs. To isolate R13's reverse optimization, a separate temporary *source projection* substituted only the exact existing PR28 fastmath header Git blob `a5c26c95cad0d91a548a8db073f59777e36d4e86`. GCC+Clang × legacy+fast under `-O1 -fsanitize=address,undefined` then all **compiled and executed EXIT 0** with LeakSanitizer enabled, empty sanitizer stderr and the *same* PCM trace hash. That projected pass is **NOT a sanitizer PASS for the unchanged full PR93 source, nor independent QA of PR28**. Do not graft the unrelated fix into this optional performance PR; only the existing PR28 owner and sole Safe Merge may handle that separate review/integration gate.
