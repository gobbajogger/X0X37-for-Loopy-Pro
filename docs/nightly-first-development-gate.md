# LoopyX0X37 — nightly-first development and production promotion gate

Status: development workflow policy proposed 2026-10-23. This document does **not** authorize a `main` merge, GitHub Pages publication, firmware distribution, physical flash, or stable release. Current owner directions and applicable repository `AGENTS.md`/maintained rules remain controlling.

## Strict order of operations

1. **Develop on owned isolated refs.** Firmware/SMC/clock/data-safety code and its tests stay in uniquely named `lane/...` branches of [`gobbajogger/X0X37-for-Loopy-Pro`](https://github.com/gobbajogger/X0X37-for-Loopy-Pro). Installer-only browser/UI work can use owned `lane/...` branches of [`gobbajogger/x0x37-for-Loopy-Pro_nightly`](https://github.com/gobbajogger/x0x37-for-Loopy-Pro_nightly). Never update production `main`, production `gh-pages`, nightly `main` or nightly `gh-pages` directly as a worker.
2. **Validate before declaring a candidate.** Use native local tests on the exact source SHA, not GitHub-hosted Actions. Run affected host/static/negative/regression checks and independent QA. For a firmware build candidate, also run actual pinned Elite and Pro DEV target builds as applicable; validate matching controller images, model/package identity, CRC/SHA-256, memory/flash/pool budgets and backup/readback/install safety. No physical keyboard is needed for source commits or host checks; missing or failing automatic gates are recorded as `WIP / NO-GO`, not silently waived. Documentation-only changes do not need a target build.
3. **Commit and deliver the development checkpoint before promotion.** After appropriate local checks, push each meaningful change only to its approved isolated lane, fast-forward and verify the actual remote SHA and changed paths. An accurately labeled incomplete source patch may be pushed as isolated WIP; this does not qualify as a build. The sole firmware Safe Merge worker combines reviewed firmware source on its isolated production-repository integration lane, not on production `main`.
4. **Record the outcome in NIGHTLY first.** The catalog owner writes truthful append-only development history (including `SOURCE ONLY`, `BUILD FAILED`, `DEV CHECKED — DEVICE NOT TESTED`, `SUPERSEDED` and missing-artifact outcomes) to its own isolated branch in the *separate* public nightly repository. Record production source ref/full commit/tree SHA and corresponding test evidence, plus per-model artifact hashes *only when actual artifacts were inspected*. No proprietary SDK/toolchain/DSP, user data, `.fwsc`, `ctl.img`, credentials, or unapproved firmware URLs may enter nightly Git. Submit a PR to NIGHTLY `main`; only its designated merger may merge independently verified eligible PRs after local `npm run build`, `npm test` and relevant UI/browser checks. A pushed source lane or nightly PR is not a nightly `main` merge.
5. **Publish the nightly preview separately.** The sole nightly Pages publisher may fast-forward approved, checked source-only website/status changes to NIGHTLY `gh-pages`; verify Git ref and served HTTP bytes independently. The nightly flashable catalogs (`preview-catalog.json`, generated `docs/versions.json` and served `versions.json`) remain empty absent individual approval of an exact fully validated distributable hardware-test DEV candidate and all applicable license, controller, package, model, backup and installer safeguards. Nightly *history* is read-only and is not an install selector.
6. **Physical validation and production gate.** The owner alone tests exact matching Elite/Pro device, controller and package identities and supplies attributable backup/readback and feature evidence. Only after the checked nightly checkpoint, all required software/package tests, matching physical-device confirmation *for a production installable firmware choice*, and separate explicit production authorization may a designated production integrator/publisher consider production updates under its maintained rules. Merely passing nightly checks never triggers an automatic production `main` or production `gh-pages` merge. `main` promotion, installer publication and stable release remain separate explicit gates.

## Enforceable checks for every scheduled worker

Before any production promotion, require a **nightly checkpoint reference**: nightly repository, remote branch or merged PR, immutable nightly commit SHA, linked exact production source SHA/tree, executed local check results and specific outstanding gates. If no matching NIGHTLY checkpoint exists, label `NIGHTLY-FIRST GATE PENDING` and continue independent testing, source review, package checks or nightly catalog work; do not change production `main` or production `gh-pages`.

Keep code source, build artifact, status metadata and deployment identities separate. Confirm the destination repository/ref before every Git write; use an owned isolated lane and non-force fast-forward operation, read back the remote SHA, and never use a refused write's alternative API/branch/encoding as a workaround. Do not overwrite another worker's branch. An automated nightly `main` PR merger is authorized **only** for eligible PRs in the nightly repository; that authorization does not extend to production `main` or nightly Pages.

A `NIGHTLY SOURCE BRANCH` / `NIGHTLY PR` / `NIGHTLY MAIN` / `NIGHTLY PAGES PUSHED` / `NIGHTLY HTTP VERIFIED` state must be reported precisely; none alone implies firmware installability, actual device PASS or production eligibility.
