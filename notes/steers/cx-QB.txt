Q2.1 **risk** firmware/hal/fm1_flash.h:204-205 `irq_save()` / `irq_restore()` and
firmware/hal/smk_input.h:630-639 `fm1__lock()`/`fm1__unlock()`.
"save" returns 0 and "restore" always runs `sti`. They are not nestable. If a function that uses
them is ever called with interrupts already off (inside another irq_save, a flash window, or an ISR),
interrupts come back on too early. Current call sites (main_fm1.c:211/771/780/2067/2314, ble.c:286/293/597/636,
plat_fm1.c:52/62/72, x0x.c:83) were checked: all of them run in the main loop, not nested. So this is
a trap for future code, not a live bug.
Fix: read the real interrupt-enable state on save (pi32v2 status register), and restore it only if it
was on. If that cannot be read safely on this SDK, add a debug nesting counter that faults on nesting
(host + X0X_DEBUG builds). Also make fm1__lock an alias of irq_save, so there is one primitive.
Test: host test with the stub irq layer: nested save/restore keeps "off" until the outer restore.
Device: no change in audio (run the existing 10-min play soak).
