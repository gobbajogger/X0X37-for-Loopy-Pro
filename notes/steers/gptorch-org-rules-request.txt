# DnBOX organization rules (draft v1, 2026-11-01)

Goal: a mistake must be impossible, not forbidden. Each rule is a gate. A gate is a script or a checklist file. If the gate fails, the next step cannot start. A promise ("I will check") is not a gate.

Repo: gobbajogger/X0X37-for-Loopy-Pro. Tools live in `tools/gates/`. Every gate prints `GATE <name> PASS|FAIL <reason>` and exits 0 or 1.

## S1. Single source of truth: docs/ROADMAP.md

1. ROADMAP.md is the only list of work. FEATURE-REGISTRY, briefs, ledgers, steers and meeting notes are inputs. They are not lists. A task that has no ROADMAP row does not exist.
2. Each row has exactly these 10 columns. `tools/gates/roadmap_lint.py` rejects any other shape.

| Column | Rule |
|---|---|
| ID | Stable, never reused, never renumbered. Form `R-NNNN` (4 digits). Old IDs (#5, M5, L6) go in `Alias`. |
| Title | ≤ 8 words, says the behavior ("PANIC on long hold of HOME"). |
| Description | One sentence: trigger → result → limits. ≥ 12 words. "item 5", "TBD", "unknown" = lint FAIL. |
| Source | Owner quote + date + place (meeting 2026-11-01, chat link, #699 line). Required. |
| Status | One of: `agreed`, `in-progress`, `in-build`, `done`, `rejected`, `owner-question`. |
| Target | Release (`0.0.25`) or `later`. `agreed` with a target = must ship in that release. |
| Models | `Elite`, `Pro`, `FM-1` (any subset). |
| Owner-thread / PR | One PR number, or `-`. One row → one PR at most. |
| Evidence | For `in-build`/`done`: `commit:<sha> test:<file or scenario>` and for UI `png:<path>`. |
| Alias / conflicts | Old numbers and IDs of rows it touches (`conflicts:R-0123`). |

3. Only the Docs Keeper writes ROADMAP.md, through PRs titled `roadmap: <IDs>`. Other agents send row changes to the Docs Keeper.
4. `roadmap_lint.py` runs in every gate below. A lint FAIL blocks all gates.
5. Other docs may not contain a status table. `tools/gates/docs_lint.py` fails if a new `.md` outside `docs/` or a table with a `Status` column outside ROADMAP.md appears in a PR.
6. Migration: convert the 174 Master tracker rows of PR #812 to the schema. M5 (unknown item) becomes one `owner-question` row with the meeting recording/notes pointer. It is the only allowed question for that meeting.

## G1. Intake gate (agreement → row → checks → thread)

Order is fixed. A step cannot start before the step above passes.
1. Record: within the same session as the agreement, the receiving agent writes the row (ID, title, full description, owner quote) into `intake/pending.md`. A meeting ends with a read-back: the agent lists every new row with its description to the owner. The owner says yes. No read-back = meeting not closed.
2. Duplicate check: `tools/gates/intake_check.py R-NNNN` searches ROADMAP titles/descriptions/aliases, FEATURE-REGISTRY, open PRs and branches (GitHub API) for the key words. It prints matches. If a match exists, the agent merges the request into the existing row (adds Source) instead of a new row.
3. Conflict check: the script lists rows that touch the same button, page, file or gesture (keyword map `tools/gates/controls.yaml`: HOME, SHIFT, FX, part buttons, faders…). Example: HOME long hold (PANIC) vs HOME + part button (sound reset) must name both. If a conflict exists, the row gets `conflicts:` and the agent writes ONE owner question (G7). Status stays `owner-question`.
4. Row lands in ROADMAP.md as `agreed` (Docs Keeper PR).
5. Only then may a thread/PR be opened (G3).

## G3. Dispatch gate

`tools/gates/dispatch_check.py <ROW-IDs> <thread-file>` must PASS before any handoff is sent. It checks:
- every ID exists and is `agreed` or `in-progress`;
- no other open PR or live thread owns the row (Owner-thread column + PR search) → stops duplicate PRs;
- the handoff file quotes the full row description for each ID (no bare numbers);
- the handoff has the fixed header: base commit, branch, models, done criteria = row Evidence fields, "do only these rows";
- the preflight lines 1–6 are present.
The script writes the thread/PR into the row. A handoff without a PASS line in its first line is invalid; receivers must refuse it.

## G4. Merge gate

`tools/gates/merge_check.py <PR>` must PASS before merge into the integration branch:
- PR title/body names ≥ 1 row ID; every changed file maps to a named row (diff hunk ↔ row, reviewer ticks per file) → scope;
- full host suite 0 fail / 0 skip; Elite and Pro build exit 0;
- no deleted or replaced `*.png`, `assets/`, `images/`, `*_private.h` file unless a row says so (`git diff --diff-filter=DR`) → stops discarded images;
- author gobbajogger; base is not `main`/`nightly`; no `.github/` change;
- no second open PR touches the same row.

## G5. Publish gate: `tools/gates/roadmap_gate.py`

Spec. Input: `--release 0.0.25 --artifacts <dir>`. Exit 1 on any FAIL. Output is pasted into the release PR.
1. Roadmap coverage: for every row with `Target = release` and status `agreed|in-progress|in-build|done`: status must be `in-build` or `done`, Evidence must have a commit that is an ancestor of the build commit (`git merge-base --is-ancestor`) and a test file that exists and ran in this suite log. Any row without it → `FAIL R-NNNN <title>: no build evidence`. `owner-question` rows with a target → FAIL (decide or move to `later` with owner quote).
2. Lint: roadmap_lint PASS, zero rows with empty Description.
3. BT controller: each Elite/Pro package contains `ctl.img`; size > 0; CRC32 equals the CRC in the build manifest; the firmware manifest flag `bt_bundled=1`. Missing → FAIL.
4. Model: each artifact name, manifest `model` field and the binary's embedded model string agree (`SMK37-ELITE`, `SMK37-PRO`, `FM1`). An FM-1 image in an SMK-37 folder, or a mismatch → FAIL. Installer has strict model match (#806).
5. Images: every PNG/asset in the previous release still exists, or a row approves its removal. Every UI row has an owner-approved framebuffer PNG path.
6. Release config: `X0X_DEV_PADCAL=0`; RAM/pool free ≥ limits.
7. Writes `release/<ver>/GATE.txt` with sha256 of every artifact. The publish step reads only artifacts listed there.

## G6. Flash gate

No device write without `tools/gates/flash_check.py --device <port>`:
- reads the device ID by query (not by USB name, not by port order). USB names are never used to pick a target. Device must answer model + serial;
- compares with the artifact manifest model and the GATE.txt sha256 → mismatch stops;
- checks a fresh slot backup exists for this serial;
- requires the latest owner grant for this model and action, quoted with time, in `flash/grants.md`;
- only one device connected, or the serial is passed explicitly.
The installer refuses to run without the token that flash_check prints.

## G7. Question gate

The owner may be asked only if `tools/gates/question_check.py "<text>"` passes:
- the answer is not in ROADMAP (Description/Source), #699, USER_PREFERENCES.md or the rules (keyword search printed);
- the question names row ID + full title + description, never a bare number;
- it is one question with labeled options (A/B) and a default;
- the row is set to `owner-question`.
Questions are batched: at most one message with questions per day (daily review), except a blocker for a device write or a conflict that stops a running build.

## G8. Scope gate

- Work exists only for an `agreed` row. A commit without a row ID in its message fails `merge_check`.
- An agent who sees a useful extra writes an `idea:` line in `intake/ideas.md`. It does not code it. The owner promotes ideas in the daily review.
- Reports list rows touched. Files changed outside the rows → merge FAIL.

## R9. Daily review (one fixed time, e.g. 20:00 Asia/Vladivostok)

`tools/gates/daily_review.py` creates one message to the owner:
1. rows changed today (ID, title, old → new status, evidence);
2. agreed rows for the next release that lack evidence (roadmap_gate dry run);
3. open PRs/threads and their rows; any PR or thread without a row;
4. batched owner questions (G7);
5. violations caught (R10).
No other status message goes to the owner that day except blockers.

## R10. Catching rule violations

- Gates are code, not reading: each gate writes a line to `gates/log.tsv` (time, agent, gate, target, PASS/FAIL).
- `tools/gates/audit.py` (in the daily review) compares: merged PRs without a merge_check PASS; handoffs without dispatch PASS; flashes without flash_check token; owner questions without question_check PASS; new docs outside S1. Each hit is a violation row.
- A violation stops the agent's lane until the Orchestrator writes a fix (rule, script change, or gate) — the fix makes the same mistake impossible next time. "Agent will be more careful" is not an accepted fix.
- Every new incident gets an F-row in section 0 and a gate change in the same day.

- The firmware, with its Bluetooth stack, must be freely shareable under an open license.
- Before you use licensed third-party code, check if we can make it again in a legally distinct way. An example is code from public specifications.
- JieLi does not publish the source of its Bluetooth controller (btctrler.a). Do not bundle JieLi files. The computer of the end user downloads them from the official source and builds the controller image locally. The controller runs as a separate image (our MPL shim, HCI mailbox, core 1).
- Keep the Bluetooth image in one contiguous flash block.
- The Bluetooth settings are in the GLOBAL menu (BLUETOOTH MIDI section). The BT buttons stay as they are, or work only in clip mode.
- The preferred delivery is an HTML web installer that gets the necessary files automatically. If possible, end users need no toolchain.

# Steps
1. Stop duplicate work. Pause routines that only re-check stopped work. Give each helper bot one job and don't pause them.
2. Split the fixes. One worker groups the integration PR's failures by root cause into a shared groups file. Other workers take the unowned groups. Side PRs run in parallel in their own directories.
3. Share the setup. Use one source snapshot and one SDK copy, ccache, incremental builds and all cores. Run the host suite and the device builds at the same time.
4. While fixing, run only the affected tests. Run the full suite plus every device build once, on the final head.
5. Gather UI mockups. Render every mockup from the real framebuffer into one folder. The owner approves them all at once, before any UI code is pushed.
6. Use a merge gate. A script checks the full logs for the exact head SHA, the approved author and committer, and that no secrets, binaries or CI files are in the diff.
7. Merge one PR at a time as each passes. Make a backup ref first, then run the gate, then merge. The merge owner does it, not the fix workers.
8. Device check. A helper writes the device test checklist during the build. Install only with the owner's OK after everything is merged.

# X0X37 roadmap

This file tells what we build, what we finished, where we are and what we must still do. Update this file when a step ends or a plan changes. USER_PREFERENCES.md gives the preferences and rules. x0x37/BEHAVIOR.md gives the intended behavior. x0x37-progress-log.md gives the detailed history.

## The goal

We make X0X firmware for the M-Vave SMK-37 (Pro and Elite). The firmware has these properties:

1. It has a clip mode that acts as an Akai APC40 mkII for Loopy Pro. The pads start clips, and the pads and the screen show the clip colours.
2. It keeps all the X0X features (sequencer, synth engines, BREAK mode) at full quality: 44.1 kHz, with no length cuts.
3. End users can import their own loops for BREAK mode, and the loops stay safe across updates.
4. It has Bluetooth MIDI (MIDI only), and it stays freely shareable under an open license.
5. End users install it from a web page, with no toolchain.
