# DnBOX work gate (mandatory, run before every step)

If any answer is no, stop and fix it first. Never skip a gate.

## 1. Intake (owner says or agrees something)
- Is it written in ROADMAP.md (the only list) with ID, description, source quote and status? If not, write it now.
- Think it through myself for live play. Do I see a flaw or a better way? Say so with my own opinion; never just agree.
- Conflict check against implemented features (buttons, combos, timing, screens) and the 122 list. Is it already a feature? Is it a duplicate?
- Never re-ask the owner about something already agreed.

## 2. Plan before build
- Has GPTOrchestrator made or approved a plan for it (order, dependencies, one PR per ROADMAP item, tests, mockup need)? If not, no builder thread starts.
- Has the owner approved the plan where it changes behavior or UI? UI already agreed needs no new mockup.

## 3. Dispatch
- Builder work goes ONLY to classic ChatGPT threads. Bots and box helpers only coordinate, relay and test.
- The handoff quotes the full ROADMAP rows and says 'do only these rows'. Nothing extra, no unrequested features.
- Is any other PR or thread already doing this? Then reuse it.

## 4. Merge
- Every changed file maps to a ROADMAP row. Extra changes are rejected.
- Full suite with no new non-environment failures, Elite and Pro builds pass, audio identity matches unless the change is intended, author is gobbajogger, no main/.github/.env/captures.
- GPTOrchestrator reviewed it with full files.

## 5. Publish
- The build is checked against ALL of ROADMAP, row by row. Any agreed row for this release that's missing gets finished first.
- package_nightly --check passes with the current bundled BT controller, the package model is correct, every image is kept, and the iPhone path is unchanged.

## 6. Flash
- Only with the owner's OK. Identify the device by its hardware/firmware-reported model, never the USB name. The package model equals the reported model. Never FM-1. No pkill. Never touch BTIF, USRTRIM, efuse, key_mac or bootloader.

## 7. Asking the owner
- Ask only about real risks he may miss (hardware, live sound, projects). Give a description, not bare numbers, plus my recommendation. Never ask what something I tracked meant.

## 8. Report
- Report the result: what got in, what didn't and why. Update ROADMAP after every merge.

Authority and enforcement
Apply platform safety and actual permissions first, then the latest explicit owner instruction for the exact scope and action. Older files, role names, workflow modes, status labels and quoted approvals cannot expand authority. Preserve applicable freezes, active ownership, cancellations and actual denials until valid superseding evidence exists.

A gate is enforced only when the action executor checks it and refuses the action on failure. A checklist, pasted PASS line, editable GATE.txt or later audit is not enforcement.

Every merge, publication and device-write route must enforce its applicable gate. Before claiming protection, verify that alternate credentials, API routes, bypass flags and raw installers cannot evade that gate within the managed execution boundary. Changes to credentials, permissions or protections require their own authorization. Until that boundary is established, report “enforcement not established”; do not pretend a voluntary script makes mistakes impossible.

Use the previously accepted gate version to assess changes to gate code or policy. A candidate cannot weaken its own acceptance criteria and approve itself.

Gate receipts come from the trusted runner and bind the operation, repository, destination, policy version, source/tree/base, scope revision, evidence and artifact hashes. The executor verifies the receipt and current inputs immediately before acting. A receipt is evidence, not permission.

One work list, one policy source

Acceptance criteria and evidence references.
Next action, receiver and completion criterion.

The gate resolves and verifies inputs; it never silently uses “latest.” It performs these checks:

RG01 Schema and provenance: valid canonical records, stable IDs, aliases, source reconciliation, authorized transitions and complete relevant input reads.

RG02 Release scope: every baseline obligation is present; all additions, deferrals, rejections, model changes and acceptance changes have valid provenance. Unresolved record-recovery gaps affecting completeness block qualification.

RG03 Behavioral coverage: every committed item/model meets its acceptance criteria on the candidate. No unresolved blocking conflicts, unsupported done claims or ancestry-only acceptance.

RG04 Evidence integrity: verify producer/reviewer identities, exact source/tree, configuration, SDK/toolchain/controller/generated-input closure, commands, complete logs, exit statuses and expected test inventory. Reject stale, fabricated, truncated or mismatched receipts.

RG05 Required qualification: full host suite and Elite/Pro builds satisfy zero-fail/zero-skip requirements; applicable audio, storage, installer, visual and other required checks pass. Host estimates do not satisfy required hardware checks.

RG06 Real package targets: parse each package and payload, verify supported model, build target, board/layout compatibility, address ranges and provenance. Filenames, manifest text and an embedded display string agreeing are not enough. Reject FM-1 payloads for SMK-37.

RG07 Bluetooth completeness: verify the actual matching controller bytes inside the assembled install package, expected digest, size, format, configuration, version compatibility and safe placement. A nonempty ctl.img, self-computed CRC or bt_bundled flag alone is insufficient. Controller reuse requires proven unchanged inputs and identical bytes.

RG08 Assets: verify retained/reference hashes, authorized changes, independent visual evidence and actual candidate renders for relevant UI work.

RG09 Release configuration and budgets: X0X_DEV_PADCAL=0; free pool at least 8192 bytes under the supplied applicable policy; no flash/RAM-region overflow; all other required model-specific limits and safety reserves satisfied. Missing limits block qualification; never invent or silently lower them.

RG10 Publication authority and content: exact destination/action permitted, required ownership present, distribution rights established and excluded material absent. No credentials, unrelated private samples, raw captures, restricted SDK/toolchain material or other prohibited bytes.

Complete install-package qualification and lawful publication are separate. If the required controller cannot lawfully be redistributed, block that publication.
