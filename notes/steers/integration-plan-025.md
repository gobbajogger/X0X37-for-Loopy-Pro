2. Live-use decisions and conflict resolution

PANIC: proposed long-hold STOP is not ready for approval as a universal gesture

The keyboard exposes PLAY toggle, not a separate STOP button. SMC note 0x5D in DAW mode is PAUSE/context-lock: immediate lock action and 900 ms hold-to-unlock behavior; it is not a free STOP key. MMC command 0x5D means STOP but has no key-up/hold duration. Numeric equality does not make those protocols the same input. A universal hold timer would steal context lock or invent a release it cannot observe.

Therefore do not implement long STOP yet, and do not move PANIC back onto HOME: HOME help and existing chords remain intact. Owner must select an actual, separately observable gesture per supported device/mode and approve any changed short action. Prior FX+SEQ/BANK-pair alternatives, if considered, are proposals only and need the same collision review. A real dedicated external STOP with press/release could be supported only under a documented device-specific mapping; its short STOP must remain immediate. That also means a long hold will already have stopped transport, conflicting with the original “PANIC keeps transport running” requirement. Owner must explicitly settle that semantic conflict.

Panic contract once the gesture is settled: local voice/note ownership, sustain/damper and queued note-ons cleared safely; explicit tracked NoteOff and appropriate all-notes-off/CC123 to each intended output, no unrelated peer leakage; no accidental project mutation; event releases cannot rearm voices or trigger HOME taps. Whether to add all-sound-off/CC120 is an owner-approved musical choice (tails versus hard kill), not an assumed replacement for tracked cleanup. Fire once per hold; cancellation on disconnect/mode change and no false firing during long FX throws. Clip NOTE REPEAT panic stays unchanged and is regression-tested.

PLAY while a question is open: recommend answer NO, then normal transport action

At supplied source ui.c:3720 and smc_mixer.c:1807, O_ASK presently intercepts transport. New proposal supersedes C8's earlier “question stays open” design, but is not accepted or implemented yet. Recommended contract: on a fresh PLAY press with O_ASK open, dispatch the existing negative-answer/cancel handler exactly once, close the question without committing destructive action, then dispatch the same transport action that input would perform without a question. Keyboard PLAY therefore starts when stopped and stops when already running. Literal “always play” would prevent stopping on the beat and diverge from normal PLAY behavior; owner must confirm normal-toggle versus force-start. True STOP, where present, cancels then stops. SMC PAUSE/context lock must retain its real protocol semantics, not be mislabeled STOP.

Preserve HOME-first PLAY redo and clip PATCH+PLAY redo precedence; do not introduce transport delay or treat releases/repeats as fresh cancel/start events. If HOME+PLAY is intended to cancel instead while a question is open, that is a separate owner decision, not an accidental consequence of router ordering. O_ASK must intercept only new semantic presses: always route prior held FX/note releases to their original captured owner, even if the question opened meanwhile. Clean up cancellation state before loading a new view; no reentrant yes branch, deferred stale callback, duplicate MMC action or stuck FX.
